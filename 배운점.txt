1. 포트 (Port) — 서버의 "호수"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 개념
  서버 = 아파트 건물, 포트 = 호수(101호, 102호...)
  한 건물에 같은 호수가 2개 있을 수 없듯이, 같은 포트를 두 프로그램이 동시에 쓸 수 없음

■ 우리 프로젝트에서 쓰는 포트
  - 5000번: PaaS 관리 사이트 (FastAPI)
  - 15000번: MSSQL 데이터베이스 (외부 서버 10.0.11.175)
  - 12001~13000번: 사용자 배포 프로젝트들 (자동 할당, 최대 1,000개)

■ 외부 포트 vs 내부 포트
  외부 포트 = 아파트 호수 (바깥에서 접근하는 번호)
  내부 포트 = 집 안의 방 (컨테이너 안에서만 쓰는 번호)

  예: 사용자가 12001번으로 접속 → Docker가 컨테이너 내부 80번(nginx) 또는 3000번(앱)으로 전달
  컨테이너끼리는 완전히 격리돼있어서 내부 포트가 겹쳐도 문제없음
  (101호 안에 거실, 102호 안에도 거실 — 다른 집이니까 OK)

■ 포트 자동 할당 (port_allocator.py)
  DB에서 이미 쓰는 포트 확인 + 실제 열려있는지 이중 체크 → 비어있는 포트 배정
  → 겹칠 일이 절대 없음

2. 방화벽 (Firewall) — 아파트 정문 경비실
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 개념
  외부에서 서버로 들어오는 접속을 허가/차단하는 문지기
  쓰는 포트만 열고, 나머지는 전부 닫는 게 원칙

■ 열어야 하는 포트
  - 5000번 (인바운드): PaaS 관리사이트 접속용
  - 12001~13000번 (인바운드): 배포된 프로젝트 접속용
  - 15000번 (아웃바운드 → 10.0.11.175): DB 연결용

■ 왜 중요한가
  DB 포트가 외부에 열려있으면 → 아무나 DB 접속 가능 → 데이터 유출
  SSH(22번)가 아무나 접근 가능하면 → 서버에 로그인 시도 가능
  안 쓰는 포트가 열려있으면 → 취약점 노출 위험

3. Docker 컨테이너 — 독립된 가상 환경
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 개념
  각 프로젝트가 독립된 "집"에서 실행됨
  한 프로젝트가 폭주해도 다른 프로젝트에 영향 없음

■ 리소스 제한
  - CPU: 1코어
  - 메모리: 512MB
  - 재시작 정책: on-failure(3) → 크래시 시 3번까지 자동 재시작

■ Dockerfile = 집 설계도
  프로젝트 유형에 따라 자동 생성됨
  - React/Vite → node:20-alpine + npm run build + serve
  - Flask → python:3.12-slim + flask run
  - FastAPI → python:3.12-slim + uvicorn
  - 정적 HTML → nginx:alpine
  - Fullstack → 2-stage 빌드 (frontend + backend)

■ 이미지 vs 컨테이너
  이미지 = 설계도 (빌드 결과물, 변하지 않음)
  컨테이너 = 설계도로 만든 실제 집 (실행 중인 인스턴스)

■ 컨테이너 상태
  running → 정상 실행 중
  exited → 프로세스 종료 (크래시 또는 정상 종료)
  → docker system prune은 exited 컨테이너를 삭제함! (주의)

■ OOM Kill
  앱이 512MB 한도를 넘기면 Docker가 강제 종료 (Out Of Memory Kill)
  → restart_policy로 3번 재시작 시도 → 3번 다 실패하면 포기

4. nginx — 웹서버/리버스 프록시
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 역할
  1) 정적 파일(HTML, CSS, JS) 서빙
  2) 리버스 프록시: 요청을 백엔드로 전달 (/api/* → backend:8000)
  3) SPA fallback: 모든 경로를 index.html로 보내줌

■ 주요 설정
  - client_max_body_size: 업로드 파일 크기 제한 (기본 1MB → 50MB로 변경)
  - Cache-Control: 브라우저 캐시 제어 (no-cache로 항상 최신 버전)
  - proxy_pass: 백엔드 서버로 요청 전달
  - try_files: SPA 라우팅 지원 ($uri → $uri/ → /index.html)

■ 실제 겪은 문제
  - 413 Request Entity Too Large: client_max_body_size 미설정 → 1MB 넘는 XML 업로드 실패
  - 캐시 문제: 배포 후 Ctrl+Shift+R 해야 최신 버전 보임 → no-cache 헤더로 해결
  - Permission denied (exit code 126): Alpine Linux에서 node_modules 실행 권한 문제

5. 환경변수 (.env) — 비밀 설정값 관리
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 왜 필요한가
  API 키, DB 비밀번호 같은 민감한 정보를 코드에 직접 넣으면 위험
  → .env 파일에 분리해서 관리

■ 빌드타임 vs 런타임
  - 빌드타임: VITE_*, NEXT_PUBLIC_* 등은 빌드 시 코드에 삽입됨
  - 런타임: Docker environment= 파라미터로 컨테이너 실행 시 주입
  - 보안: Dockerfile에서 `RUN rm -f .env` → 최종 이미지에 시크릿 미포함

■ 실제 겪은 문제
  - Fullstack에서 backend/.env를 못 찾음 → 루트에서만 탐색했기 때문
    → 하위 폴더 .env 탐색 기능 추가로 해결
  - .env에 같은 키가 2줄 → 나중 값이 덮어씌움 (디버깅 어려움)
  - 시스템 환경변수가 .env보다 우선 → unset으로 초기화 필요

6. 배포 (Deployment) — 코드를 서버에 올리기
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 우리가 쓰는 방식
  로컬에서 tar.gz 압축 → scp로 서버 전송 → 서버에서 압축 풀기 → 서비스 재시작

■ 배운 주의사항
  - SCP -r 사용 금지: Windows에서 파일이 제대로 안 올라감 → tar.gz로 통째 압축
  - docker system prune -af 금지: exited 컨테이너까지 삭제 → 사용자 프로젝트 사라짐
  - rm -rf /opt/paas/workspaces/* 금지: 배포 중인 워크스페이스 날릴 수 있음
  - 프로세스 확인: 서버 재시작 시 기존 프로세스가 안 죽는 경우 있음 (ps aux로 확인)
  - __pycache__: Python 컴파일 캐시가 옛날 코드를 기억함 → 삭제 필요할 때 있음

■ 서비스 관리 명령어
  - sudo lsof -t -i :5000 → 5000번 포트 쓰는 프로세스 찾기
  - sudo kill -9 {pid} → 프로세스 강제 종료
  - nohup python main.py > ~/paas.log 2>&1 & → 백그라운드 실행 (SSH 끊어도 유지)
  - tail -f ~/paas.log → 실시간 로그 보기

7. 헬스체크 (Health Check) — 서비스 감시
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 개념
  30초마다 "이 서비스 살아있어?" 확인하는 것

■ 체크 방법
  1) Docker 컨테이너 상태 확인 (running인지)
  2) HTTP 요청 보내서 응답 오는지 확인

■ 동작
  - Running 프로젝트: 연속 3회 실패 → Stopped로 변경
  - Stopped 프로젝트: 컨테이너 살아있고 HTTP OK → Running으로 자동 복구

■ 실제 겪은 문제
  - 프로젝트가 접속은 되는데 대시보드에서 Stopped 표시
    → 헬스체커가 일시적 실패로 Stopped 처리했는데 복구가 안 됨
    → Stopped 자동 복구 기능 추가로 해결

8. API — 서버와 통신하는 방법
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ REST API 기본
  - GET: 데이터 조회 (프로젝트 목록, 상태 확인)
  - POST: 데이터 생성 (배포 요청, 로그인)
  - PUT/PATCH: 데이터 수정 (환경변수 변경)
  - DELETE: 데이터 삭제 (프로젝트 삭제)

■ HTTP 상태 코드 (실제 만난 것들)
  - 200: 성공
  - 400: 잘못된 요청 (API 크레딧 부족 등)
  - 401: 인증 실패 (API 키 틀림)
  - 413: 요청 크기 초과 (client_max_body_size)
  - 429: 요청 너무 많음 (Rate Limit)
  - 502: Bad Gateway (컨테이너 앱이 죽었음)

■ API 키 관리
  - Anthropic: sk-ant-xxx 형식, 크레딧 기반 과금
  - OpenAI: sk-proj-xxx 형식, 크레딧 기반 과금
  - 무료 크레딧 소진 시 → 400 에러 (credit balance too low)
  - API 키는 절대 코드에 하드코딩하면 안 됨 → .env로 관리

9. AI 힐링 — 빌드 오류 자동 수정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 3단 구조
  규칙 기반 감지 (90%) → AI 폴백 (10%) → Node.js 폴백 (최후)

■ 규칙 기반 = 뼈대
  "이 프로젝트가 Flask인지, Vite인지, Fullstack인지" 큰 틀을 잡아줌
  → 빠르고 정확, 대부분의 프로젝트를 커버

■ AI = 살
  "그 틀 안에서 터지는 예측 불가능한 디테일"을 잡아줌
  → 같은 Flask라도 Pillow 쓰면 libjpeg-dev, psycopg2 쓰면 libpq-dev 필요
  → 분기로 다 넣으면 이미지가 커지고 느려짐, AI가 실패 시에만 추가하니 효율적

■ AI Dockerfile 생성
  규칙으로 판별 못 하는 프로젝트 → AI가 파일 구조 분석해서 Dockerfile 직접 생성
  → 빌드 전에 개입 (힐링은 빌드 후)

■ AI 힐링
  빌드 실패 → 에러 로그 + 프로젝트 파일 분석 → Dockerfile/requirements.txt 수정
  → 최대 5회 재시도
  → Rate limit 감지 시 5분간 자동 차단

■ 비용
  - 호출당 약 $0.01~0.03
  - 무료 크레딧 $5 → 소진되면 과금 필요
  - Anthropic에서 OpenAI로 전환 (비용 이슈)

10. 서버 부하 관리 — 성능과 안정성
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 부하가 거의 없는 것들
  - 헬스체커 (30초마다): Docker API = 로컬 소켓 통신 (네트워크 비용 0)
  - 배포 큐 워커: asyncio.Queue 대기 시 CPU 0%
  - 캐시 방지 헤더: HTTP 헤더 1줄 추가일 뿐

■ 제한 걸어놓은 것들
  - 컨테이너당 CPU 1코어, 메모리 512MB → 한 프로젝트가 서버 전체를 먹는 것 방지
  - 디스크 80% → 경고, 90% → 신규 배포 차단
  - AI 호출 Rate limit → 429 2회 시 5분간 차단
  - 배포 파이프라인: 10분 타임아웃

■ 서버 자원 확인 명령어
  - docker stats --no-stream: 각 컨테이너 CPU/메모리 사용량
  - df -h: 디스크 사용량
  - free -h: 서버 전체 메모리
  - ps aux | grep python: 프로세스 확인

11. Python 프로젝트 자동 감지 — 개발자 편의
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ requirements.txt 없는 프로젝트
  .py 파일의 import문 스캔 → pip 패키지 자동 매핑 → requirements.txt 생성
  예: from openai import OpenAI → openai 패키지 필요

■ requirements.txt 있지만 불완전한 프로젝트
  import 스캔 → 빠진 패키지 자동 추가
  예: 코드에서 openai 쓰는데 requirements.txt에 없음 → 자동 보완

■ 비표준 엔트리포인트
  main.py, app.py 외에도 web_app.py, run.py 등 감지
  파일 내용에서 Flask(__name__), FastAPI() 패턴으로도 탐지

■ 배포 신호 (deploy signal)
  ZIP에 이 파일들 중 하나라도 있으면 배포 가능 판정:
  index.html, package.json, requirements.txt, main.py, app.py,
  server.js, web_app.py, run.py, server.py 등 17종+

12. Fullstack 프로젝트 — 프론트+백엔드 통합
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 자동 감지
  ZIP 안에 frontend(package.json) + backend(requirements.txt/main.py) 2개 폴더
  → 자동으로 fullstack으로 인식

■ 컨테이너 1개로 통합
  nginx(프론트 서빙 + API 프록시) + backend(uvicorn/flask)
  supervisord로 두 프로세스 동시 관리

■ 실제 겪은 문제
  - backend에서 from app.xxx import → ModuleNotFoundError
    → PYTHONPATH 추가로 해결
  - backend에 requirements.txt 없음 → Dockerfile COPY 실패
    → import 스캔 자동 생성으로 해결
  - backend/.env를 못 찾음 → 하위 폴더 탐색으로 해결

13. 보안 — 최소한의 방어
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 적용된 보안 조치
  - Supabase Service Role Key 스캔: 프론트엔드 코드에 노출 시 배포 거부
  - .env 이미지 미포함: Dockerfile에서 RUN rm -f .env
  - 시크릿 영속화: _project_secrets/ (chmod 600)
  - ZIP 경로 트래버설 방어: ../ 포함 경로 차단
  - JWT 인증: 로그인 토큰 기반 인증

■ API 키 관리 교훈
  - 코드에 절대 하드코딩 금지
  - .env 파일로 분리
  - 환경변수가 중복되면 디버깅 지옥 (마지막 값이 이김)
  - 시스템 환경변수 > .env 파일 (우선순위 주의)

14. 디버깅 — 문제 해결 능력
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 로그 확인이 기본
  - 서버 로그: tail -f ~/paas.log
  - 컨테이너 로그: docker logs paas-{프로젝트명}
  - 실시간 로그: docker logs -f paas-{프로젝트명}

■ 실제 디버깅 경험
  - 502 Bad Gateway → 컨테이너 로그 확인 → Python import 에러 발견
  - 413 Entity Too Large → nginx client_max_body_size 문제
  - 401 Unauthorized → API 키가 .env에서 제대로 안 읽힘 → 시스템 환경변수 충돌
  - Permission denied (126) → chmod 타이밍 문제 (COPY가 chmod 뒤에 덮어씌움)
  - CSS 깨짐 → Jinja2 템플릿이 렌더링 안 됨 → Flask가 아닌 nginx로 배포된 것

■ 배운 디버깅 원칙
  1) 에러 메시지를 정확히 읽자
  2) 로그를 먼저 확인하자
  3) 로컬에서 되는데 서버에서 안 되면 → 환경 차이를 의심하자
  4) 설정 파일 변경 후 → 서비스 재시작 확인하자
  5) 프로세스가 진짜 죽었는지 → ps aux로 확인하자

15. 설계 철학 — 어떻게 만들 것인가
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 기존 동작을 건드리지 말고, 케이스를 추가하라
  - 기존에 잘 되던 게 깨지면 안 됨
  - 새 기능은 else 분기나 폴백으로 추가
  - 예: requirements.txt 있으면 기존 동작, 없으면 자동 생성 (추가)

■ 규칙 기반 + AI 폴백 = 최적의 조합
  - 규칙: 빠르고 예측 가능, 90%의 케이스 커버
  - AI: 느리지만 유연, 예외 케이스 대응
  - 모든 걸 규칙으로 → 이미지 비대화 / 모든 걸 AI로 → 느리고 비쌈

■ 자동화할 수 있으면 자동화하라
  - requirements.txt 자동 생성/보완
  - Dockerfile 자동 생성
  - .env 자동 감지/머지
  - 헬스체크 자동 복구
  - 배포 신호 자동 탐색

■ 실패에 대비하라
  - AI 힐링 최대 5회
  - 파이프라인 10분 타임아웃
  - 디스크 90% 시 배포 차단
  - Rate limit 감지 시 자동 차단

1. 서버는 "아파트"고, 포트는 "호수"다
2. Docker 컨테이너는 독립된 "집"이다 — 격리, 리소스 제한, 재시작 정책
3. nginx는 만능 문지기 — 정적 파일 서빙, 프록시, 캐시 제어, 크기 제한
4. 환경변수는 비밀 금고 — 코드에 절대 하드코딩 금지
5. 로그는 진실의 거울 — 문제가 생기면 로그부터 봐라
6. 기존을 건드리지 말고 케이스를 추가하라 — 안전한 확장 원칙
7. AI는 만능이 아니다 — 규칙 기반이 90%, AI는 예외용 안전망
8. 배포는 신중하게 — docker system prune 한 줄로 사용자 데이터 날릴 수 있음
